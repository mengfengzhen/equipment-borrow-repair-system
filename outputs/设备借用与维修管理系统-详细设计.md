# 设备借用与维修管理系统详细设计

## 1. 项目定位

本项目是一个面向企业内部设备资产管理、借用审批、领取归还、维修处理和统计分析的全栈演示系统。系统目标不是简单 CRUD，而是完整展示业务闭环、状态流转、权限控制、数据一致性和可演示的后台管理体验。

面试展示重点：

- 后端建模能力：设备、借用申请、审批、维修、日志之间的关系清楚。
- 业务规则能力：设备不可重复预约、未审批不可领取、损坏归还必须进入维修等。
- 工程能力：模块化后端、类型安全、统一异常、权限守卫、种子数据、一键启动。
- 前端完整度：标准后台布局、表格筛选、表单弹窗、详情时间线、统计卡片。
- 演示闭环：管理员、普通用户、部门负责人、维修人员可以完成一条真实业务链路。

## 2. 技术选型

### 2.1 推荐技术栈

前端：

- React
- TypeScript
- Vite
- Ant Design
- React Router
- TanStack Query 或 Axios 封装

后端：

- NestJS
- TypeScript
- Prisma ORM
- SQLite
- JWT
- class-validator
- Swagger OpenAPI

数据库：

- 开发和演示阶段使用 SQLite。
- 数据库是本地文件，不需要安装 MySQL、PostgreSQL 或其他数据库服务。
- 后续如果部署到线上，可平滑迁移到 PostgreSQL。

### 2.2 选择理由

React + Ant Design 适合快速搭建企业后台，表格、表单、标签、弹窗、抽屉、统计卡片都有成熟组件。

NestJS 适合展示全栈工程师的后端能力。它比 Express 更规范，有 Controller、Service、Module、Guard、DTO、Pipe、Interceptor 等结构，面试时更容易说明架构设计。

Prisma 适合快速建模和迁移数据库。它可以生成类型安全的数据库访问层，降低 SQL 细节负担，同时保留清晰的数据模型。

SQLite 对当前情况最友好。你电脑没有数据库，SQLite 不需要单独安装服务，项目内一个文件即可运行。

## 4. 核心业务流程

### 4.1 主流程

1. 管理员新增设备，设备初始状态为可用。
2. 普通用户查看设备列表和设备详情。
3. 普通用户选择设备，填写借用时间、归还时间、用途和备注，提交借用申请。
4. 系统校验设备状态和时间段冲突。
5. 部门负责人或管理员审批申请。
6. 审批通过后，设备进入已预约状态。
7. 管理员确认设备已领取。
8. 设备进入借出状态。
9. 用户归还设备。
10. 管理员登记归还状态。
11. 如果设备正常，设备恢复可用。
12. 如果设备损坏、缺件或异常，系统自动创建维修记录，设备进入维修中。
13. 维修人员处理维修。
14. 维修完成后，设备恢复可用、报废，或保持维修相关状态。

### 4.2 面试演示脚本

推荐演示路径：

1. 使用 admin 登录，新增一台“索尼 A7M4 相机”。
2. 切换 user，申请借用该设备，选择明天到后天。
3. 切换 manager，审批通过申请。
4. 切换 admin，确认领取。
5. 查看设备状态从可用变为借出。
6. 模拟另一个用户在重叠时间段申请同一设备，系统提示时间冲突。
7. 回到 admin，登记归还，选择“设备损坏”。
8. 系统自动生成维修记录，设备进入维修中。
9. 切换 repair，填写维修结果并标记已修复。
10. 查看设备恢复可用，历史记录和操作日志完整。

## 5. 状态设计

### 5.1 设备状态 DeviceStatus

| 状态 | 含义 | 是否可申请 |
| --- | --- | --- |
| AVAILABLE | 可用 | 是 |
| RESERVED | 已预约 | 视时间段而定 |
| BORROWED | 借出 | 否 |
| REPAIRING | 维修中 | 否 |
| SCRAPPED | 报废 | 否 |
| DISABLED | 停用 | 否 |

### 5.2 借用申请状态 BorrowStatus

| 状态 | 含义 | 允许操作 |
| --- | --- | --- |
| PENDING_APPROVAL | 待审批 | 审批、驳回、要求补充 |
| NEED_MORE_INFO | 需补充信息 | 申请人补充、重新提交 |
| APPROVED | 已通过 | 确认领取 |
| REJECTED | 已驳回 | 只读 |
| PICKED_UP | 已领取 | 登记归还 |
| RETURNED | 已归还 | 只读 |
| CANCELLED | 已取消 | 只读 |
| OVERDUE | 逾期未归还 | 登记归还、提醒 |

### 5.3 维修状态 RepairStatus

| 状态 | 含义 |
| --- | --- |
| REPAIRING | 维修中 |
| WAITING_PARTS | 待配件 |
| FIXED | 已修复 |
| UNREPAIRABLE | 无法修复 |

### 5.4 归还结果 ReturnCondition

| 状态 | 含义 | 后续动作 |
| --- | --- | --- |
| NORMAL | 正常 | 设备恢复可用 |
| DAMAGED | 损坏 | 自动进入维修 |
| MISSING_PARTS | 缺件 | 自动进入维修 |
| ABNORMAL | 异常 | 自动进入维修 |

## 6. 核心业务规则

1. 已借出、维修中、报废或停用的设备不能申请借用。
2. 同一设备在同一时间段不能被多个用户预约或借用。
3. 未审批通过的申请不能领取设备。
4. 审批通过后，设备在对应时间段内被占用。
5. 管理员确认领取后，设备状态变为借出。
6. 设备逾期未归还时，需要显示逾期状态。
7. 归还时发现损坏、缺件或异常，设备必须进入维修流程。
8. 设备维修完成前不能再次借用。
9. 报废和停用设备不能被借用。
10. 普通用户只能查看和操作自己的申请。
11. 部门负责人只能审批本部门申请。
12. 管理员可以查看全部设备、申请、维修和日志。
13. 所有关键状态变化必须写入操作日志。

### 8.3 后端高级设计点

#### 状态流转集中管理

设备状态、借用状态、维修状态不能散落在各个 Controller 里修改。所有状态变化都放在 Service 方法中完成，并统一写日志。

例如：

- approveBorrowRequest
- pickupBorrowRequest
- returnBorrowRequest
- createRepairFromReturn
- finishRepair

#### 时间段冲突校验

提交申请时检查同一设备是否存在重叠的有效申请。

有效状态包括：

- PENDING_APPROVAL
- APPROVED
- PICKED_UP
- OVERDUE

时间重叠条件：

```text
existing.borrowStartAt < new.borrowEndAt
AND
existing.borrowEndAt > new.borrowStartAt
```

#### 权限守卫

后端需要实现：

- JwtAuthGuard：必须登录。
- RolesGuard：限制角色。
- Ownership check：普通用户只能操作自己的申请。
- Department check：部门负责人只能审批本部门申请。

#### 操作日志

关键动作必须记录：

- 新增设备
- 修改设备
- 提交借用申请
- 审批通过
- 审批驳回
- 要求补充信息
- 确认领取
- 登记归还
- 创建维修记录
- 更新维修状态
- 设备报废或停用

- 维修中：紫色。
- 停用/报废：灰色。

不建议做移动 App 风格。全栈面试更适合稳定、清楚、专业的后台系统。

## 11. 部署方案

### 11.1 本地演示方案

本地演示需要：

- Node.js 20 或 22
- npm 或 pnpm
- 项目源码

不需要额外安装数据库。

启动方式可以设计为：

```bash
npm install
npm run setup
npm run dev
```

其中：

- setup 执行 Prisma 迁移和种子数据。
- dev 同时启动前端和后端。

本地访问：

- 前端：http://localhost:5173
- 后端：http://localhost:3000/api
- Swagger：http://localhost:3000/docs

### 11.2 线上部署方案一：前后端分开部署

适合最终给面试官一个访问链接。

需要：

- GitHub 仓库
- 前端部署到 Vercel 或 Netlify
- 后端部署到 Render、Railway、Fly.io 或类似平台
- 线上数据库 PostgreSQL

推荐组合：

- 前端：Vercel
- 后端：Render
- 数据库：Render PostgreSQL 或 Neon PostgreSQL

需要准备的环境变量：

前端：

```text
VITE_API_BASE_URL=https://your-api-domain.com/api
```

后端：

```text
DATABASE_URL=postgresql://...
JWT_SECRET=...
PORT=3000
CORS_ORIGIN=https://your-frontend-domain.com
```

注意：

- SQLite 不适合多数 serverless 或临时文件系统环境。
- 真正线上部署建议切换 PostgreSQL。
- Prisma 从 SQLite 切 PostgreSQL 需要调整 provider 和数据库 URL，模型大部分可以保留。

### 11.3 线上部署方案二：单体部署

也可以让 NestJS 托管前端构建产物。

流程：

1. 前端 build 生成 dist。
2. 后端静态托管 client/dist。
3. 一个服务同时提供前端页面和 API。

优点：

- 只有一个部署地址。
- CORS 问题少。
- 面试演示方便。

缺点：

- 工程拆分没有前后端分开部署那么标准。
- 后续扩展性略弱。

### 11.4 Docker 部署

可选增强项。

如果时间足够，可以提供：

- Dockerfile
- docker-compose.yml
- PostgreSQL 服务
- 后端服务
- 前端构建或 Nginx 服务

面试展示时 Docker 是加分项，但不是第一优先级。优先保证业务闭环完整。

## 13. MVP 范围

- 登录和角色权限。
- 设备新增、编辑、筛选、详情。
- 借用申请提交。
- 申请审批。
- 确认领取。
- 登记归还。
- 异常归还进入维修。
- 维修完成。
- 操作日志。
- 工作台统计。
- 种子数据。

## 14. 需要确认的问题

当前设计里有几个默认假设：

1. 借用审批由部门负责人或管理员完成，不做复杂多级审批。
2. 部门负责人只能审批本部门普通用户的申请。
3. 附件上传第一版可以先做成可选增强，核心演示不依赖它。
4. 设备同一时间段不能重复预约，系统按申请借用开始和预计归还时间判断冲突。
5. 线上部署如果要正式访问，建议使用 PostgreSQL，而不是 SQLite。

如果这些假设没有问题，就可以按本设计从 0 搭建项目。
